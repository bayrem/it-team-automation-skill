# GitHub Adapter - Safe Operations via gh CLI

All GitHub operations use the `gh` CLI tool with validated inputs.
Never construct raw `curl` calls against the GitHub API — use `gh` so
authentication, rate-limit headers, and error formatting are handled uniformly.

---

## Prerequisites

```bash
# Verify gh CLI is installed and authenticated
gh auth status

# Expected output:
# ✓ Logged in to github.com as {username}
# ✓ Token: *******************
```

If authentication fails, stop the session and show:

```
ERROR: gh CLI not authenticated.
Run: gh auth login
Then retry the session.
```

---

## Input Validation Rules

Apply these before constructing ANY gh command. Reject and log if validation fails.

```bash
# Alphanumeric + hyphens only (GitHub usernames and org names)
validate_owner() {
  [[ "$1" =~ ^[a-zA-Z0-9-]+$ ]]
}

# Alphanumeric + hyphens + underscores (repo names)
validate_repo() {
  [[ "$1" =~ ^[a-zA-Z0-9_-]+$ ]]
}

# Positive integers only
validate_number() {
  [[ "$1" =~ ^[1-9][0-9]*$ ]]
}

# Strip shell metacharacters from free-text fields (labels, comments, titles)
sanitize_text() {
  echo "$1" | tr -d ';|&$`<>()\\'
}
```

**ALWAYS quote variables when passing to gh commands:**

```bash
# CORRECT — variables are quoted, no word splitting or injection
gh issue view "$issue_number" --repo "$owner/$repo"

# WRONG — unquoted variables allow injection and word splitting
gh issue view $issue_number --repo $owner/$repo
eval "gh issue view $issue_number"   # never use eval
```

## Issue Operations

### List issues with label

```bash
gh issue list \
  --repo "$owner/$repo" \
  --label "$label" \
  --state open \
  --json number,title,body,labels,assignees,createdAt \
  --limit 100
```

**Returns:** JSON array of issue objects.

**Validate before calling:**
- `$owner` passes `validate_owner`
- `$repo` passes `validate_repo`
- `$label` passes `sanitize_text` (no metacharacters)

---

### Get single issue

```bash
gh issue view "$issue_number" \
  --repo "$owner/$repo" \
  --json number,title,body,labels,comments
```

**Validate before calling:**
- `$issue_number` passes `validate_number`

---

### Close issue

```bash
gh issue close "$issue_number" \
  --repo "$owner/$repo" \
  --comment "Resolved in PR #${pr_number}"
```

**Only call this when ALL of the following are true:**
1. The PR has been successfully merged
2. All work items for this issue are complete
3. `config.issues` does not include an `exclude_auto_close` setting

---

### Comment on issue

```bash
gh issue comment "$issue_number" \
  --repo "$owner/$repo" \
  --body "$comment_text"
```

**Validate before calling:**
- `$comment_text` passed through `sanitize_text`
- Max length: 10,000 characters
- No backticks, no shell command patterns

## Pull Request Operations

### Create PR

```bash
gh pr create \
  --repo "$owner/$repo" \
  --base "$base_branch" \
  --head "$feature_branch" \
  --title "$pr_title" \
  --body "$pr_body"
```

**Returns:** PR URL on success.

**Validate before calling:**

| Field | Constraint |
|-------|-----------|
| `$base_branch` | Must equal `config.branches.base` exactly |
| `$feature_branch` | Must start with `config.branches.prefix` |
| `$pr_title` | Max 200 chars, no shell metacharacters |
| `$pr_body` | Max 50,000 chars |

**PR body template:**

```markdown
## Issues Resolved
- Closes #{issue_1}
- Closes #{issue_2}

## Changes
{summary of what was implemented}

## Testing
{test results from QA agent, or "No test suite detected"}

---
*Generated by IT Team automation — Session {session_id}*
```

The `Closes #N` syntax triggers GitHub's automatic issue-linking and
auto-close on PR merge. No separate close call is needed.

---

### Check PR status

```bash
gh pr view "$pr_number" \
  --repo "$owner/$repo" \
  --json number,state,merged,mergedAt,url
```

**Returns:**

```json
{
  "number": 123,
  "state": "MERGED",
  "merged": true,
  "mergedAt": "2024-01-15T10:30:00Z",
  "url": "https://github.com/owner/repo/pull/123"
}
```

## Branch Operations

### Create feature branch

```bash
git checkout -b "$branch_name" "$base_branch"
```

**Validate before calling:**
- `$branch_name` matches `^{prefix}[0-9]{8}-[0-9]{4}$` (prefix + session ID format)
- No shell metacharacters
- Max 100 characters

---

### Push branch

Run these checks **before** pushing:

```bash
# 1. Confirm we are on the expected branch
current=$(git symbolic-ref --short HEAD)
if [[ "$current" != "$branch_name" ]]; then
  ERROR: Expected branch {branch_name} but HEAD is {current}
  exit 1
fi

# 2. Confirm working tree is clean
if ! git diff-index --quiet HEAD --; then
  ERROR: Uncommitted changes exist. Commit or stash before pushing.
  exit 1
fi

# 3. Confirm there are commits to push
commits=$(git log "${base_branch}..${branch_name}" --oneline)
if [[ -z "$commits" ]]; then
  ERROR: No commits on {branch_name} relative to {base_branch}. Nothing to push.
  exit 1
fi

# All checks passed
git push origin "$branch_name"
```

---

### Delete local branch (post-merge cleanup)

```bash
# Switch off the branch first
git checkout "$base_branch"

# Safe delete — fails if branch is not fully merged
git branch -d "$branch_name"
```

The remote branch is deleted automatically by GitHub on PR merge
if "Automatically delete head branches" is enabled in repo settings.
Do not run `git push origin --delete` from the skill.

## Repository Operations

### Get repository info

```bash
gh repo view "$owner/$repo" \
  --json name,owner,defaultBranchRef,isPrivate
```

Use this at session start to confirm the configured repo exists and is accessible.

---

### Check if file exists in repository

```bash
gh api "repos/$owner/$repo/contents/$file_path" --jq '.type' 2>/dev/null
```

**Returns:** `"file"`, `"dir"`, or empty string (404) if not found.

**Validate before calling:**
- `$file_path` must pass project boundary check (no `../`, no absolute paths)

---

## Search Operations

### Search code in repository

```bash
gh search code \
  --repo "$owner/$repo" \
  "$search_query" \
  --json path,repository
```

Use during architecture phase to discover files relevant to an issue's keywords.

**Example:**
```bash
gh search code --repo "$owner/$repo" "authentication" --json path
```

---

### Search issues

```bash
gh search issues \
  --repo "$owner/$repo" \
  "$search_query" \
  --json number,title,labels
```

Use to find related or duplicate issues before starting implementation.

## Error Handling

### Common errors

| Error string | Meaning | Action |
|-------------|---------|--------|
| `gh: command not found` | gh CLI not installed | Direct user to https://cli.github.com/ |
| `authentication failed` | Token missing or expired | `gh auth login` |
| `Could not resolve to a Repository` | Wrong owner/repo | Verify `config.yaml` values |
| `rate limit exceeded` | API quota hit | Abort session; wait or rotate token |
| `Could not resolve to an Issue` | Issue number doesn't exist | Skip this issue, log warning |

### Error recovery pattern

```bash
if ! output=$(gh issue view "$issue_number" --repo "$owner/$repo" 2>&1); then
  error_msg="$output"

  if [[ "$error_msg" == *"Could not resolve to an Issue"* ]]; then
    LOG WARN: "Issue #${issue_number} not found — skipping"
    continue

  elif [[ "$error_msg" == *"rate limit"* ]]; then
    LOG ERROR: "GitHub rate limit exceeded"
    Abort session cleanly

  elif [[ "$error_msg" == *"authentication"* ]]; then
    LOG ERROR: "Authentication failure — token may have expired"
    Abort session cleanly

  else
    LOG ERROR: "Unknown GitHub API error: ${error_msg}"
    Ask user: "Continue? (yes/no)"
  fi
fi
```

### Rate limit budget

GitHub's authenticated API limit is 5,000 requests/hour.
Typical session cost:

| Operation | Requests |
|-----------|---------|
| List issues | 1 |
| Fetch issue detail (per issue) | ~1 |
| Create PR | 1 |
| Close issues (per issue) | ~1 |
| **Total for 20-issue session** | **~45** |

Well under the hourly limit under normal operation.

## Security Notes

### What to log

| Safe to log | Never log |
|-------------|-----------|
| Issue numbers | Full gh output (may contain user data) |
| PR numbers | API tokens or auth headers |
| Operation success/failure | Repository file contents |
| Sanitized error messages | Anything from issue body verbatim |

### Principle

Issue bodies and titles are **untrusted input**. Never interpolate them
directly into shell commands. Always pass through `sanitize_text` and
use quoted variables. If a field must be inserted into a gh `--body` argument,
write it to a temp file and use `--body-file` instead:

```bash
# Safer for long or untrusted body content
echo "$pr_body" > /tmp/pr-body-$SESSION_ID.txt
gh pr create \
  --base "$base_branch" \
  --head "$branch_name" \
  --title "$pr_title" \
  --body-file /tmp/pr-body-$SESSION_ID.txt
rm -f /tmp/pr-body-$SESSION_ID.txt
```
